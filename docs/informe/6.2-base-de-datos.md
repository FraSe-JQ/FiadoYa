# 6.2 Base de datos

El motor seleccionado es MySQL 8.4.7, por su persistencia relacional, transacciones InnoDB, claves foráneas, restricciones y compatibilidad con JPA y Flyway. Las migraciones reales están en backend/src/main/resources/db/migration. Hibernate valida el esquema y no lo crea automáticamente.

El modelo definitivo, diccionario de columnas y relaciones se generan a partir de las migraciones reales y se describen en [modelo de datos](../modelo-base-de-datos.md). Las entidades se encuentran en Model.java. Los roles se representan como un conjunto cerrado de valores de users.role; una imagen se guarda como URL en products; el cronograma y la obligación son la misma entidad payment_obligations. Las condiciones históricas se almacenan en purchases.terms_json y las versiones de condiciones del cliente en credit_terms.

Una compra registra tienda, cuenta, responsable, fecha, moneda, modalidad, plazo, capital, gracia, corte y periodo cero. purchase_items conserva nombres, cantidades y ambos precios originales. payment_obligations conserva todas las filas del cronograma. payments registra recepción, componentes de pago, responsable, fecha y saldo de capital posterior; payment_allocations vincula cada obligación cancelada. billing_cycles conserva instantáneas históricas por cuenta/corte.

Las restricciones únicas impiden duplicación de correo, membresías, documentos por tienda, códigos de producto, claves de compra/pago y asignaciones de obligaciones. Los índices de cuentas/fechas y vencimientos apoyan consultas. El repositorio adquiere bloqueo pesimista y refresca la cuenta; READ_COMMITTED permite comprobar el saldo actualizado. El aislamiento de tienda se valida también en Access: una FK aislada no reemplaza autorización.

Las consultas reproducibles se encuentran en [scripts/sql-evidence.sql](../../scripts/sql-evidence.sql). Las evidencias SQL deben obtenerse contra la instancia ejecutada y no mediante capturas ficticias.
